# Контекст

Задача IPRSV1-13: прислан список портов, которые должны быть открыты на входе
машины `VDSWIN2K22` (Windows Server 2022, Timeweb VDS) — это стандартный
портовый набор платформы CMSV6, которая на этой машине и работает. Нужно
проверить, что из списка уже открыто, и открыть недостающее.

Список из задачи, дословно:

- TCP: `443, 16601, 16603, 16604, 16605, 16607, 16608, 16609, 16611, 6602, 6617,
  6604, 6630-6635, 6601, 6602-6612, 2121-2162, 20000-21000, 30000-31000, 80,
  8080, 88, 8088, 6601-6612`
- UDP: `6604, 6602-6612, 20000-21000, 30000-31000, 6603-6609, 6611`

Диапазон через тире — включительно; дубли и вложенные диапазоны игнорируются.
После свёртки дублей получается ровно это (сверено вручную, границы
включительно) — именно этот нормализованный список и есть предмет задачи:

**TCP — 15 записей, 2076 портов:**
`80`, `88`, `443`, `2121-2162`, `6601-6612`, `6617`, `6630-6635`, `8080`,
`8088`, `16601`, `16603-16605`, `16607-16609`, `16611`, `20000-21000`,
`30000-31000`

**UDP — 3 записи, 2013 портов:**
`6602-6612`, `20000-21000`, `30000-31000`

Обратить внимание: в UDP-списке **нет 6601** (там только `6602-6612`), и в UDP
нет ни 6617, ни 6630-6635, ни 80/88/443/8080/8088/16xxx. Списки разные, свести
их в один нельзя.

Состояние машины на 31.08.2026 (из `CLAUDE.md` в корне репозитория, замеры того
же дня):

- Входящие включённые разрешающие правила файрвола: `GPS services TCP 2`
  (TCP 7000, 9966, 9967, 7500, 20021, 22), `nginx 80` (TCP 80), `nginx 443`
  (TCP 443), `OpenSSH Server (sshd)` (TCP 22), плюс вендорские
  `GPSNginx`/`GPS *` с протоколом Any — их портовый охват в `CLAUDE.md` не
  раскрыт. То есть из нашего списка про 80, 443 и одиночный 20021 известно, что
  они открыты, а про остальное по документации сказать нельзя.
- Слушатели: tomcat CMSV6 на 80, nginx на 443, sshd на 22, RDP 3389, Zabbix
  Agent 10050, CMSV6 — 2121 и 14147 (FTPd), 6601–6613, 6617, 6625 (только
  loopback), 6630–6635, 9999, MySQL 127.0.0.1:3311.
- frps не работает с 17.08.2026, порты 7000/9966/9967/7500 никто не слушает.
  Это отдельная незакрытая проблема машины, в этой задаче она не решается и не
  упоминается в критериях.
- 30.07.2026 на машине существовали правила `CMSv6-6601-6612-tcp`,
  `CMSv6-6601-6612-udp`, `CMSv6-6631-6635-tcp`,
  `CMSv6-2121-2122-6617-2162-8080-tcp`, `Zabbix`, `OpenSSH 2299`. В списке от
  31.08.2026 их уже нет: CMSV6 с тех пор переустанавливали, и правила могли
  быть переименованы в семейство `GPS *` либо удалены. Вывод для этой задачи:
  фактический охват портов берётся только замером на машине, документация тут
  не источник истины.
- Апстрим-провайдер порты не фильтрует — проверено соединением с раннера
  30.07.2026, косвенно подтверждено 31.08.2026 (80/443/22 отвечают снаружи).
  Значит единственный шлюз — Windows Defender Firewall; в панели Timeweb
  ничего открывать не нужно.

**Почему делаем двумя сводными правилами на весь список, а не точечно
«только недостающие».** Буквальное «открыть недостающие» требует вычесть из
списка охват вендорских правил `GPS *` с протоколом Any, а он неизвестен и
менялся уже дважды при переустановках CMSV6. Правила файрвола складываются по
ИЛИ, дубликат разрешения ничего не ломает и ничего не расширяет, поэтому два
своих правила на полный список: (1) дают ровно требуемый результат независимо
от того, что там у вендора; (2) не переживают чужое переименование — если
вендорское правило снова исчезнет, порты останутся открытыми; (3) проверяются
одной командой вместо разбора пяти чужих правил. Проверка «что уже было
открыто» при этом никуда не девается — она остаётся отдельным шагом с отчётом,
потому что это вторая половина постановки.

# Что сделать

Вся работа — на сервере по SSH плюс правка `CLAUDE.md` в репозитории. Кода в
репозитории нет, собирать и тестировать нечего.

**0. Подключение.** SSH, **порт 22** — реквизиты из переменной/секретов
репозитория `SERVER`, `LOGIN`, `PASSWORD` (в сессии раннера это `$SERVER`,
`$LOGIN`, `$PASSWORD`), либо ключ `~/.ssh/id_ed25519`. Порт 2299 из старых спек
в `specs/` больше не существует — на него не ходить. Многострочный PowerShell
подавать только через `-EncodedCommand` (base64 от UTF-16LE), не через stdin, и
первой строкой каждого скрипта ставить `$ProgressPreference =
'SilentlyContinue'` — иначе `Get-NetFirewallRule` заливает stdout
CLIXML-прогрессом. Обе ловушки описаны в `CLAUDE.md`, раздел «Connecting to the
server».

**1. Замер до изменений — только чтение, ничего не менять.** Собрать три
факта и сохранить их в отчёт стадии (они же потом идут в `CLAUDE.md`):

- **Полная инвентаризация входящих разрешающих правил.** Все включённые
  входящие правила с их протоколом и портами. Соединение правила с его
  портовым фильтром делать по одному правилу за раз — коллекцию правил в
  `Get-NetFirewallPortFilter` целиком передавать нельзя, привязка «правило →
  порты» при этом теряется:
  ```powershell
  Get-NetFirewallRule -Direction Inbound -Action Allow -Enabled True |
    ForEach-Object { $pf = $_ | Get-NetFirewallPortFilter
      [pscustomobject]@{ Rule=$_.DisplayName; Proto=$pf.Protocol
                         Ports=($pf.LocalPort -join ',') } }
  ```
  По этой таблице посчитать и записать в отчёт, какие записи нормализованного
  списка уже покрыты, какие покрыты частично, какие не покрыты вовсе —
  отдельно по TCP и по UDP. Это и есть ответ на «проверить, какие уже
  открыты», он нужен в чате задачи как результат, а не только как промежуточный
  шаг.
- **Слушатели.** `Get-NetTCPConnection -State Listen` и `Get-NetUDPEndpoint` —
  какие из портов списка реально кем-то заняты. Нужно для шага 3: порт без
  слушателя снаружи не ответит даже с открытым файрволом.
- **Динамический диапазон портов Windows.** `netsh int ipv4 show dynamicport
  tcp` и `netsh int ipv4 show dynamicport udp`. Ожидается стандартное начало
  49152 — тогда пересечения с `20000-21000` и `30000-31000` нет и всё в
  порядке. **Если диапазон окажется переопределён и пересечётся с любой
  записью нашего списка — правила не создавать, остановиться и сообщить
  Максиму**: входящее разрешение на эфемерный диапазон открыло бы наружу
  локальные порты исходящих соединений, а это уже не то, что просили.

**2. Создать два правила файрвола.** Правила по порту, не по программе — как
сделаны существующие правила машины (`CMSv6-*`, `nginx 443`).

Имена ровно такие (префикс свой, чтобы правила не попадали под запрет
«не трогать `CMSv6-*`/`GPS *`» и было видно, откуда они взялись):
`iprsv1-13-ports-tcp` и `iprsv1-13-ports-udp`.

Перед созданием проверить, нет ли правила с таким же `DisplayName`
(`Get-NetFirewallRule -DisplayName 'iprsv1-13-ports-tcp' -ErrorAction
SilentlyContinue`). Windows разрешает несколько правил с одинаковым именем, так
что повторный прогон без этой проверки наплодит дубликаты — если правило уже
есть, сначала `Remove-NetFirewallRule` по этому имени, потом создать заново.

```powershell
New-NetFirewallRule -DisplayName 'iprsv1-13-ports-tcp' `
  -Direction Inbound -Action Allow -Enabled True `
  -Protocol TCP -Profile Any -RemoteAddress Any -Program Any `
  -LocalPort @('80','88','443','2121-2162','6601-6612','6617','6630-6635',
               '8080','8088','16601','16603-16605','16607-16609','16611',
               '20000-21000','30000-31000') `
  -Description 'IPRSV1-13, 31.08.2026: CMSV6 platform port set, vendor list'

New-NetFirewallRule -DisplayName 'iprsv1-13-ports-udp' `
  -Direction Inbound -Action Allow -Enabled True `
  -Protocol UDP -Profile Any -RemoteAddress Any -Program Any `
  -LocalPort @('6602-6612','20000-21000','30000-31000') `
  -Description 'IPRSV1-13, 31.08.2026: CMSV6 platform port set, vendor list'
```

`-Profile Any` обязателен: на машине включены все три профиля. Правила
применяются сразу — ни перезагрузка, ни перезапуск служб не нужны и не
делаются.

**3. Проверка после изменений.**

- `Get-NetFirewallPortFilter` по обоим новым правилам возвращает ровно те
  списки портов, что заданы на шаге 2, а сами правила — `Enabled: True`,
  `Direction: Inbound`, `Action: Allow`, все три профиля.
- Повторная полная инвентаризация входящих разрешающих правил (та же команда,
  что на шаге 1) отличается от снимка «до» **только** двумя новыми правилами:
  ни одно чужое правило не изменено, не отключено и не удалено.
- Снаружи, с раннера, проверить TCP-подключение к тем портам списка, у которых
  на шаге 1 нашёлся слушатель и которые до этого не были покрыты. Без установки
  новых утилит, средствами bash:
  ```bash
  for p in 2121 6605 6617 6632; do
    timeout 5 bash -c "</dev/tcp/$SERVER/$p" && echo "$p open" || echo "$p closed"
  done
  ```
  Порты подобрать по факту замера; 2121 (FTPd), 6605 и 6617 (платформа), 6632
  (6630-6635) — ожидаемый набор, если слушатели на месте.
- Контроль без регрессии: `http://scanvision.online/` и
  `https://scanvision.online/` по-прежнему отвечают 200.
- **Что проверкой снаружи не подтверждается и провалом не считается:** порты
  без слушателя (например 88, 8080, 8088, свободные части `20000-21000` и
  `30000-31000`, все 16xxx, если там ничего не поднято) снаружи не ответят —
  для них доказательством является только наличие правила. UDP снаружи
  подключением не проверяется вовсе: без ответчика на той стороне отличить
  «открыт» от «закрыт» нельзя, поэтому для UDP критерий — только правило.

**4. Обновить документацию.** Modify: `CLAUDE.md` в корне репозитория.

- Раздел `### Firewall (inbound, enabled)` — привести к фактическому снимку
  после работы: добавить `iprsv1-13-ports-tcp` и `iprsv1-13-ports-udp` с их
  нормализованными списками портов, поправить перечень остальных правил по
  замеру шага 1 (в частности — что на самом деле стало с правилами
  `CMSv6-*` от 30.07.2026), поставить дату проверки.
- Записать измеренный динамический диапазон портов Windows и подтверждение,
  что он не пересекается со списком.
- Записать две ловушки, если они подтвердятся на практике: Windows допускает
  несколько правил с одинаковым `DisplayName`, поэтому повторное применение
  требует сначала удалить старое одноимённое; порт с правилом, но без
  слушателя, снаружи не отвечает — это не признак закрытого файрвола.
- Обновить дату последнего сквозного замера в `README.md`, если правишь его
  раздел с датой.
- Значения `LOGIN`/`PASSWORD`/`SERVER` и токен frps в документацию, коммиты,
  PR и логи не попадают — только имена переменных (раздел `## Secrets`).

**Отдельно, вне критериев готовности:** список от вендора расширяет входную
поверхность машины примерно на 4 тысячи портов, а на машине уже есть известные
открытые проблемы (дашборд frps на 7500 наружу с парой `admin`/`admin`,
незашифрованный приватный ключ на рабочем столе). Это не повод не делать
задачу — набор нужен платформе — но при отчёте стоит одной строкой напомнить
Максиму про 7500.

# Критерии готовности

1. В отчёте стадии есть таблица «что из нормализованного списка было открыто до
   работы» — отдельно TCP и UDP, с указанием, каким именно правилом покрыт
   каждый пункт, и с явным перечнем непокрытых. Это результат первой половины
   постановки, он должен быть виден в чате задачи.
2. На машине существуют два включённых входящих разрешающих правила
   `iprsv1-13-ports-tcp` (протокол TCP) и `iprsv1-13-ports-udp` (протокол UDP),
   по одному экземпляру каждого, профиль Any, remote address Any, и их портовые
   фильтры совпадают с нормализованным списком из раздела «Контекст»
   один в один: TCP — 15 записей, UDP — 3 записи.
3. Снимок всех входящих разрешающих правил «после» отличается от снимка «до»
   только этими двумя правилами. Ни одно существующее правило не изменено, не
   отключено, не удалено.
4. Подключение снаружи (с раннера) проходит для тех портов списка, у которых
   есть слушатель. Порты без слушателя и весь UDP подтверждаются наличием
   правила — их недоступность снаружи провалом не считается.
5. `http://scanvision.online/` и `https://scanvision.online/` по-прежнему
   отвечают 200 — топология входа не пострадала.
6. Динамический диапазон портов Windows измерен и с записями списка не
   пересекается (либо, при пересечении, правила не созданы и задача
   остановлена с сообщением Максиму — это тоже валидный финал).
7. `CLAUDE.md` обновлён по факту: новые правила, фактический список остальных
   правил, измеренный динамический диапазон, дата проверки. В документации нет
   значений секретов.
