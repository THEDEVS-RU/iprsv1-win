# Контекст

Задача IPRSV1-2: подключиться к серверу проекта IPRSV1 (Windows Server 2022) с
реквизитами из Actions-секретов/переменных репозитория `THEDEVS-RU/iprsv1-win` и
убедиться, что машина работает и с ней всё в порядке.

Эта спека заменяет ранее закоммиченную `specs/2026-07-30-iprsv1-win-remote-health-check.md`
(тот же репозиторий, ветка `dev`). Ту спеку исполнять не нужно: она стоит на двух
предположениях, которые разведка этой стадии опровергла прямыми замерами —
(1) имена секретов и переменных неизвестны и их надо выяснять отдельным
прогоном-«инвентаризацией»; (2) до машины можно дойти по WinRM или SSH,
достаточно попробовать оба протокола.

Факты, установленные замерами 2026-07-30 (детали — в «Что уже есть»):

- реквизиты заведены как реквизиты самого репозитория: переменная `SERVER` со
  значением `72.56.0.219` и секреты `LOGIN` и `PASSWORD`. Окружений (environments)
  в репозитории нет, org-уровень для этого репозитория не используется. Значения
  секретов GitHub не отдаёт ни одному токену — они расшифровываются только внутри
  прогона workflow этого репозитория, поэтому проверка обязана жить в GitHub
  Actions, а не в скрипте, запускаемом где-то ещё;
- снаружи у машины открыт ровно один порт — `3389/RDP`. Порты 22 (SSH),
  5985 и 5986 (WinRM), 445, 135, 139, 47001, 5900, 80, 443, 8080, 8443, 1433 не
  отвечают. Исходящий трафик на 22 с хоста-замерщика при этом проходит (контроль
  по `github.com:22`), то есть закрыт именно вход на машине;
- машина в момент замера жива и это действительно Windows Server 2022:
  RDP-негоциация выбирает CredSSP/NLA, TLS 1.2, self-signed сертификат
  `CN=vdswin2k22`, NTLM-челлендж отдаёт имя `VDSWIN2K22` и версию
  `10.0 build 20348`, часы машины совпадают с реальным временем.

Отсюда механизм задачи. Полный отчёт о здоровье (диски, службы, журнал событий)
требует канала выполнения команд, а снаружи такого канала нет: RDP командной
строки не даёт. Без чьих-либо действий на самой машине автоматически проверяемо
ровно три вещи, и они дают однозначный ответ «сервер работает»: доступность
3389, идентичность машины (имя и билд ОС), валидность `LOGIN`/`PASSWORD` через
NLA-рукопожатие. Глубокий отчёт workflow снимает сам, если порт 22 окажется
открыт с раннера GitHub, а если нет — помечает его недоступным и печатает два
конкретных способа открыть канал, не роняя прогон.

Репозиторий публичный, логи прогонов видны всем, поэтому IP машины маскируется
в логе, а состав отчёта ограничен тем, что перечислено ниже.

# Что сделать

Create: `.github/workflows/health-check.yml` — единственный новый файл задачи.
Один job `health`, `runs-on: ubuntu-latest`, `timeout-minutes: 10`,
`permissions: contents: read`. Все шаги — `shell: bash`.

**1. Триггеры.** Ручной запуск плюс автозапуск при изменении самого файла, чтобы
прогон состоялся на ветке реализации до слияния (кнопка `workflow_dispatch`
появляется только для workflow, уже присутствующего в ветке по умолчанию, а она
здесь `dev`):

```yaml
on:
  workflow_dispatch:
  push:
    paths:
      - '.github/workflows/health-check.yml'
```

**2. Маскировка и передача реквизитов.** Первым шагом job — `echo "::add-mask::${SERVER}"`
для `${{ vars.SERVER }}`: переменные, в отличие от секретов, GitHub не маскирует,
а репозиторий публичный. Реквизиты попадают в шаги только через `env:`
(`SERVER: ${{ vars.SERVER }}`, `LOGIN: ${{ secrets.LOGIN }}`,
`PASSWORD: ${{ secrets.PASSWORD }}`), в командную строку значения подставляются
только через раскрытие переменных окружения, `set -x` не включается.

**3. Инструменты.** `sudo apt-get update` и установка двух пакетов:

```bash
sudo apt-get install -y nmap
sudo apt-get install -y freerdp2-x11 || sudo apt-get install -y freerdp3-x11
RDP_BIN="$(command -v xfreerdp || command -v xfreerdp3)"
```

Если ни один из пакетов FreeRDP не установился или `RDP_BIN` пуст — шаг падает с
явным сообщением, что проверка учётных данных невозможна; остальные шаги при
этом должны отработать (`if: always()` на шагах 4, 5, 8).

**4. Шаг «Порты».** `nmap -Pn -n -p 3389,22,5985,5986 --open -oG - "$SERVER"`.
Результат по каждому порту (`open` / `filtered|closed`) сохраняется в
`$GITHUB_ENV` (`PORT_3389`, `PORT_22`, `PORT_5985`, `PORT_5986`) — от `PORT_22`
зависит шаг 7. ICMP на машине не проверяется (`-Pn` обязателен).

**5. Шаг «Идентичность».** `nmap -Pn -n -p 3389 --script rdp-ntlm-info "$SERVER"`
— скрипт отдаёт `NetBIOS_Computer_Name`, `DNS_Computer_Name`, `Product_Version`
и `System_Time` без всякой аутентификации. Из вывода вытаскиваются имя машины,
версия ОС и время машины, и сверяются с эталоном из «Что уже есть»:

- имя машины не `VDSWIN2K22` или версия не `10.0.20348` → красный прогон с
  формулировкой «отвечает не та машина»;
- расхождение времени машины с временем раннера больше 120 секунд →
  предупреждение в отчёте (прогон остаётся зелёным);
- если сам скрипт не смог опознать RDP на 3389 — красный прогон.

**6. Шаг «Учётные данные».** Проверка через NLA-рукопожатие без открытия сессии:

```bash
"$RDP_BIN" /v:"$SERVER" /u:"$LOGIN" /p:"$PASSWORD" /sec:nla /cert:ignore \
  +auth-only /timeout:15000
```

Разбор исхода по коду возврата и тексту ошибки FreeRDP:

- код 0 → реквизиты приняты, RDP-стек машины исправен;
- `ERRCONNECT_LOGON_FAILURE` → повторить попытку один раз, добавив
  `/d:VDSWIN2K22` (учётная запись локальная, домена у машины нет: NetBIOS-домен
  совпадает с именем машины). Если и вторая попытка даёт logon failure —
  красный прогон с формулировкой «`LOGIN`/`PASSWORD` не подходят»;
- `ERRCONNECT_ACCESS_DENIED` или отказ на уровне прав RDP → предупреждение
  «реквизиты приняты, но у учётной записи нет прав входа по RDP», прогон
  остаётся зелёным: машина при этом заведомо жива;
- таймаут или обрыв соединения при открытом 3389 → красный прогон.

Значение `PASSWORD` не печатается и не пишется в файлы; вывод FreeRDP
публикуется как есть — секреты в логе GitHub маскирует сам.

**7. Шаг «Глубокий отчёт» (условный: `if: env.PORT_22 == 'open'`).**
`sudo apt-get install -y sshpass`, затем одна неинтерактивная сессия:

```bash
SSHPASS="$PASSWORD" sshpass -e ssh -o StrictHostKeyChecking=accept-new \
  -o ConnectTimeout=10 "$LOGIN@$SERVER" \
  'powershell -NoProfile -NonInteractive -Command "<команда сбора>"'
```

Команда сбора отдаёт один JSON (`ConvertTo-Json -Compress -Depth 4`) с полями:

- `Get-ComputerInfo`: `CsName`, `OsName`, `OsVersion`, `OsBuildNumber`;
- аптайм: `(Get-CimInstance Win32_OperatingSystem).LastBootUpTime`;
- тома: `Get-Volume` по каждому тому с буквой — размер, свободно, процент
  свободного;
- память: `TotalVisibleMemorySize` и `FreePhysicalMemory` из
  `Win32_OperatingSystem`; загрузка CPU: `(Get-CimInstance Win32_Processor).LoadPercentage`;
- службы: `Get-Service | Where-Object { $_.StartType -eq 'Automatic' -and $_.Status -ne 'Running' }`
  — имена списком;
- события уровней Critical и Error за 24 часа:
  `Get-WinEvent -FilterHashtable @{LogName='System','Application'; Level=1,2; StartTime=(Get-Date).AddHours(-24)}`
  — счётчики по уровням отдельно и 10 последних записей (время, лог, источник, ID);
- признак ожидающей перезагрузки: наличие ключа реестра
  `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired`.

Если `PORT_22` не `open` — шаг не выполняется, а отчёт шага 8 пишет, что
глубокая проверка недоступна, и печатает два способа её включить: (а) поставить
на машину self-hosted runner этого репозитория — наружу не открывается ни один
порт, раннер ходит только исходящим HTTPS; (б) включить на машине OpenSSH Server
(`Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0`, служба `sshd` в
автозапуск, правило файрвола на 22). Первый способ помечается как
рекомендуемый, второй — как открывающий порт управления в интернет под парольной
аутентификацией. Оба требуют однократного входа человека на машину и в этой
задаче не выполняются.

**8. Шаг «Отчёт» (`if: always()`).** Всё собранное — в `$GITHUB_STEP_SUMMARY`:
первой строкой вердикт `OK` или `ПРОБЛЕМЫ` со списком сработавших условий, затем
таблица «проверка → результат» (порты, идентичность, реквизиты, глубокая
проверка), затем таблицы глубокого отчёта, если он выполнялся, и блок
предупреждений.

**9. Красный прогон.** Job завершается ошибкой, если: порт 3389 не открыт; RDP
на 3389 не опознан; имя машины или билд ОС не совпали с эталоном; обе попытки
аутентификации дали logon failure; обрыв или таймаут при открытом 3389. Если
выполнился шаг 7 — дополнительно: на любом томе свободно меньше 10%; не в
состоянии `Running` любая из служб `TermService`, `EventLog`, `Dhcp`,
`Dnscache`, `LanmanWorkstation`, `W32Time`; за 24 часа есть хотя бы одно событие
уровня Critical. Всё остальное — предупреждение в отчёте при зелёном прогоне:
недоступность глубокой проверки, `ERRCONNECT_ACCESS_DENIED`, прочие
Automatic-службы не в `Running` (у отложенного автозапуска это нормальное
состояние), события уровня Error, ожидающая перезагрузка, расхождение часов,
несовпадение отпечатка RDP-сертификата.

# Критерии готовности

- В ветке реализации лежит `.github/workflows/health-check.yml` с ручным
  триггером и автозапуском при изменении самого файла.
- Workflow отработал минимум один прогон, и в задачу приложены ссылка на прогон
  и его вердикт.
- В summary прогона есть строка вердикта (`OK` либо `ПРОБЛЕМЫ` с перечислением
  причин) и таблица «проверка → результат» по всем четырём проверкам: порты,
  идентичность машины, учётные данные, глубокая проверка.
- В логе прогона нет ни значения `PASSWORD`, ни незамаскированного значения
  `SERVER`.
- Проверка учётных данных дала однозначный исход: приняты, не подходят, либо
  приняты без прав RDP — с указанием кода или текста ошибки FreeRDP.
- Если порт 22 с раннера закрыт, отчёт содержит пометку о недоступности
  глубокой проверки и оба способа её включить, а прогон при этом не красный по
  этой причине.
- Если порт 22 оказался открыт, в summary есть таблицы глубокого отчёта: диски,
  память и CPU, аптайм, службы, счётчики событий за 24 часа, признак ожидающей
  перезагрузки.
