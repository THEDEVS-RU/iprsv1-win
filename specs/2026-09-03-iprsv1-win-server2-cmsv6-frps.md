# Контекст

Задача IPRSV1-18: развернуть на НОВОМ сервере `200.165.238.242` (Windows,
логин `Administrator`) тот же функционал, что работает на текущем сервере
`201.34.132.26`, — платформу CMSV6 и `frps`. Домена у нового сервера пока нет,
поэтому TLS-часть текущего сервера (nginx на 443, win-acme, сертификат
GlobalSign, записи DNS зоны `scanvision.online`) в эту задачу НЕ входит.
Отдельным требованием: CMSV6 ставится не той версии, что на текущем сервере, а
конкретной сборкой по ссылке Яндекс.Диска, указанной в задаче.

Текущий сервер `201.34.132.26` — рабочий прод. В этой задаче он только
источник знаний (его состояние описано в `CLAUDE.md` этого репозитория);
менять на нём нельзя ничего.

Факты, снятые прямыми замерами 03.09.2026 с раннера (не предположения):

- **Снаружи у `200.165.238.242` открыт ровно один порт — 3389/RDP.** TCP-проверка
  портов 22, 80, 443, 445, 5985, 5986, 7000 — все `closed/filtered`. То есть
  канала выполнения команд снаружи нет вообще: ни SSH, ни WinRM, ни SMB. RDP
  командной строки не даёт (это же было установлено для текущего сервера в
  `specs/2026-07-30-iprsv1-win-remote-health-check-2.md`).
- **Автоматизировать первый шаг (включение SSH) из пода-раннера нечем.**
  Проверено в поде: `xfreerdp`/`xfreerdp3`, `xdotool`, `Xvfb`, `nmap`
  отсутствуют, `sudo` и `apt` в поде нет вообще — доустановить FreeRDP и
  сымитировать ввод в RDP-сессии невозможно. Вариант «собрать GitHub Actions
  workflow с FreeRDP и слепым вводом клавиш» отвергнут осознанно: он требует
  завести в репозитории новые секреты с реквизитами нового сервера и вслепую
  печатать команды в GUI администратора ради шага, который человек делает за
  две минуты. Поэтому **шаг 0 выполняет человек в RDP-сессии**, по готовому
  блоку команд из «Что сделать»; всё остальное делается автоматически по SSH.
- **Файл CMSV6 по ссылке задачи опознан** (публичный API Яндекс.Диска,
  `public_key=https://disk.yandex.ru/d/D0EuilVJaJgwOA`):
  имя `CMSServerV6_WIN_7.36.1_20251023 (1).exe`, размер `1 439 442 850` байт,
  `md5 = 02938b295d681b817a02347c24bceee6`,
  `sha256 = 46b36f5ae107681317291c1e34c7376a465e564e6390c82a77fdf2ab8c548f23`.
  Это версия **7.36.1_20251023** — она СТАРШЕ той, что стоит на текущем сервере
  (`7.37.2_20260710`); «особая версия» здесь означает именно эту сборку, а не
  более новую. Ставить строго её.
- **Инсталлятор — Inno Setup 5.5** (прочитаны сигнатуры в первых 400 КБ файла:
  `Inno Setup Setup Data (5.5.0) (u)`, `Inno Setup Messages (5.5.3) (u)`).
  Значит тихая установка по SSH принципиально возможна ключами Inno Setup
  (`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP- /LOG=`), а не только GUI —
  это снимает главный риск задачи.
- **Ключ раннеров доступен**: `kubectl -n ai-runners get secret iprsv1-win-ssh`
  из пода читается, публичная половина
  (`jsonpath='{.data.id_ed25519\.pub}'`, base64) — комментарий
  `ai-runner@ai-runners`. Тот же ключ уже стоит на текущем сервере.
- **Бинарь frps 0.17.0 под Windows доступен официально**:
  `https://github.com/fatedier/frp/releases/download/v0.17.0/frp_0.17.0_windows_amd64.zip`
  (проверено через GitHub API). Версию менять нельзя: `frpc` на регистраторах —
  0.17.0 (linux/arm, зафиксировано в логе текущего сервера), а протокол frp
  между мажорными версиями несовместим.

Два решения, принятые здесь по итогам разведки, и почему:

1. **`subdomain_host = scanvision.online` задаётся и на новом сервере, хотя
   домена у него нет.** frps сопоставляет `subdomain` только по HTTP-заголовку
   `Host`, DNS при этом на стороне сервера не участвует. Если ключ не задать
   (как решили 30.07.2026 для текущего сервера, когда домена не было ни у кого),
   frps отклоняет регистрацию любого http-прокси с `subdomain` сообщением
   `subdomain is not supported because this feature is not enabled by frps` — и
   ни один регистратор на новом сервере не поднимется, то есть «такого же
   функционала» не получится. Ценность ключа — одна строка конфига; значение
   выбрано то же, что на рабочем сервере, чтобы будущее подключение домена
   свелось к записи DNS без правки конфига.
2. **`token` на новом сервере — новый, случайный, не копия боевого.** Один
   общий токен на два независимых хоста означает, что компрометация нового
   сервера роняет и старый. Следствие, которое надо записать в документацию:
   перевод регистратора на новый сервер требует правки и `<ServerIp>`, и
   `<TokenForCon>`, а не только адреса.

# Что сделать

Работа идёт по SSH на `200.165.238.242` плюс правка документации в этом
репозитории. Реквизиты (`Administrator` и пароль) — в описании задачи IPRSV1-18
на доске и в промпте стадии; в репозиторий, в PR, в коммиты и в чат их не
писать (правило «Secrets» в `CLAUDE.md`).

🔴 **Переменные окружения `SERVER`/`LOGIN`/`PASSWORD` в сессии раннера и
секреты репозитория указывают на СТАРЫЙ сервер `201.34.132.26`.** В этой задаче
их использовать нельзя ни в одной команде: подставленный по привычке `$SERVER`
выполнит установку на боевой машине. Адрес нового сервера везде задаётся явной
константой.

**0. Включение SSH — делает человек в RDP-сессии (шаг-блокер).**
Сначала проверить, не открыт ли уже порт 22 на `200.165.238.242` (возможно,
человек выполнил блок до старта стадии). Если открыт — шаг пропускается. Если
закрыт — опубликовать в чат задачи ровно этот блок и ждать ответа человека,
дальше не идти:

```powershell
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service sshd -StartupType Automatic
Start-Service sshd
New-NetFirewallRule -DisplayName "OpenSSH Server (sshd)" -Direction Inbound `
  -Protocol TCP -LocalPort 22 -Action Allow -Profile Any
```

Ничего, кроме этих четырёх команд, человека просить не нужно: ключ раннеров
ставится дальше уже по SSH. Признак успеха — TCP-подключение на 22 с раннера.

**1. Первый вход и инвентаризация.** Зайти паролем
(`sshpass -p "<пароль из задачи>" ssh -o StrictHostKeyChecking=accept-new Administrator@200.165.238.242`)
и снять исходное состояние машины, чтобы оно попало в документацию:
версия и билд ОС (`systeminfo`), имя машины, часовой пояс, свободное место на
`C:` (нужно не меньше 20 ГБ: 1,4 ГБ инсталлятор + распаковка + БД), список
служб и слушателей (`Get-NetTCPConnection -State Listen`), уже существующие
правила файрвола, уже установленный софт. Отдельно проверить, не стоит ли уже
что-то из CMSV6/frp/MySQL — если стоит, остановиться и доложить, спека
рассчитана на чистую машину.

Многострочный PowerShell подавать только через `-EncodedCommand` (UTF-16LE →
base64), не на stdin: подача на stdin молча обрывается на первом многострочном
`foreach`/`if`/`try` с кодом 0 (проверено на текущем сервере, см. `CLAUDE.md`).
Первой строкой любого скрипта, читающего `Get-NetFirewallRule`/
`Get-ScheduledTask`, ставить `$ProgressPreference = 'SilentlyContinue'`.

**2. Ключ раннеров.** Положить публичную половину ключа
`ai-runner@ai-runners` в `C:\ProgramData\ssh\administrators_authorized_keys`
(именно туда: `sshd_config` для группы администраторов читает этот файл, а не
профильный `.ssh/authorized_keys`). Ключ брать из кластера, не из текста:

```bash
kubectl -n ai-runners get secret iprsv1-win-ssh -o jsonpath='{.data.id_ed25519\.pub}' | base64 -d
```

Права на файл — как требует OpenSSH под Windows: снять наследование, оставить
`Administrators` и `SYSTEM` (`icacls ... /inheritance:r /grant ...`). Проверить
вход по ключу отдельной сессией; после этого пароль в командах больше не
использовать.

**3. Скачивание и установка CMSV6 7.36.1_20251023.** Прямая ссылка Яндекс.Диска
живёт недолго — получать её на самом сервере в момент скачивания, а не
подставлять заранее:

```powershell
$api = 'https://cloud-api.yandex.net/v1/disk/public/resources/download?public_key=https%3A%2F%2Fdisk.yandex.ru%2Fd%2FD0EuilVJaJgwOA'
$href = (Invoke-RestMethod -Uri $api).href
curl.exe -L -o C:\install\CMSServerV6_WIN_7.36.1_20251023.exe $href
```

Перед установкой обязательно сверить контрольную сумму скачанного файла с
`sha256`/размером из «Контекста» (`Get-FileHash -Algorithm SHA256`) — 1,4 ГБ по
HTTP через нестабильный канал обрывается тихо. Не совпало — перекачать, не
ставить.

Установка тихая, ключами Inno Setup:

```
C:\install\CMSServerV6_WIN_7.36.1_20251023.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP- /LOG=C:\install\cmsv6-install.log
```

Запускать через планировщик задач или `Start-Process -Wait`, помня, что процесс,
запущенный интерактивно по SSH, умирает вместе с сессией. Проверка результата —
не по коду возврата, а по фактам: появились службы `GPSDaemon`,
`GPSGatewaySvr`, `GPSMediaSvr`, `GPSLoginSvr`, `GPSUserSvr`, `GPSDownSvr`,
`GPSStorageSvr`, `GPSDataProcSvr`, `GPSGeocodeSvr`, `GPSFtpd`, `gpstomcat6`,
`GPSMysqld`; MySQL слушает `127.0.0.1:3311`; веб платформы отвечает локально.
Если тихая установка не отработала (нет служб, лог обрывается на диалоге) —
не подбирать ключи вслепую: доложить в чат и предложить человеку поставить
платформу в RDP-сессии тем же инсталлятором, это штатный путь вендора
(на текущем сервере CMSV6 ставит и переставляет не наша сторона).

**4. Порт веб-платформы 80.** Вендорский инсталлятор ставит коннектор tomcat на
8080; на текущем сервере платформа отвечает на 80, и функциональный паритет
означает 80. Прочитать `PathName` службы `gpstomcat6` (путь установки меняется
от версии к версии — на новом сервере это дерево `7.36.1_20251023`, не
`7.37.2_20260710`), в `tomcat\conf\server.xml` этого дерева поменять `port="8080"`
на `port="80"` у коннектора `Http11Nio2Protocol`, сохранив рядом копию исходного
файла, и перезапустить `gpstomcat6`.

🔴 Не добавлять в коннектор `address="127.0.0.1"`: десктопный клиент CMSV6
ходит на порт платформы напрямую, при loopback-бинде он виснет в `SynSent`.
Перезапуск `gpstomcat6` штатно занимает около 3,5 минут — это не зависание,
процесс не убивать.

**5. Адрес, который платформа отдаёт клиентам.** В БД `1010GPS` (MySQL на
`127.0.0.1:3311`, реквизиты — в
`tomcat\webapps\gpsweb\WEB-INF\classes\config\jdbc.properties` внутри дерева
установки) сначала `SELECT * FROM server_info` — таблицу после установки
заполняет вендор, вставлять свои строки нельзя. В строке `ID=3` (`IDNO='M1'`,
`Name='Media Server'`) значения `IPClient` и `LanIP` должны быть
`200.165.238.242` (домена нет, публикуется голый IP). Если там уже этот адрес —
не трогать; если другой — `UPDATE` только этих двух колонок.
`IPDevice`/`PortDevice`/`PortClient` не менять ни при каких условиях: по ним
подключаются GPS-устройства, а не браузеры.

Перед правкой снять дамп таблицы (`mysqldump`) рядом с установкой, не в
репозиторий. Изменения вступают в силу только после перезапуска `GPSLoginSvr`
(служба читает таблицу один раз при старте). Проверка — с самого сервера:
`GET http://127.0.0.1:6605/3/1?MediaType=1&Type=0&AVType=1&DevIDNO=<любой ID устройства>&Channel=0`,
в ответе `server.clientIp`/`lanip` должны показывать `200.165.238.242`.
Поле `IsHttps` остаётся `0` — это правильное состояние для сервера без TLS.

**6. frps 0.17.0.** Скачать
`https://github.com/fatedier/frp/releases/download/v0.17.0/frp_0.17.0_windows_amd64.zip`,
распаковать `frps.exe` в `C:\frps` (тот же путь, что на текущем сервере),
сверить `frps.exe -v` → `0.17.0`. Create: `C:\frps\frps.ini`, формат INI,
раздел `[common]` (эта сборка не понимает TOML/YAML), ключи ровно такие:

```ini
bind_port = 7000
vhost_http_port = 9966
vhost_https_port = 9967
subdomain_host = scanvision.online
tcp_mux = true
dashboard_addr = 127.0.0.1
dashboard_port = 7500
dashboard_user = admin
dashboard_pwd = <сгенерировать на сервере, не меньше 20 символов>
token = <сгенерировать на сервере, не меньше 24 символов>
allow_ports = 65535
max_ports_per_client = 1
log_file = C:/frps/frps-run.log
log_way = file
log_level = info
log_max_days = 30
```

Три вещи, каждая из которых уже ломала текущий сервер:

- ключ пароля дашборда — **`dashboard_pwd`**, а не `dashboard_passwd`:
  вендорские примеры используют второе имя, а парсер 0.17.0 молча игнорирует
  неизвестный ключ и оставляет дашборд с `admin`/`admin` без единой ошибки;
- `log_file` пишется **прямыми слэшами**: обратный слэш ломает разбор конфига
  (`\U` в `Users` читается как недопустимый escape), и frps молча выходит, не
  написав ни строки лога;
- `dashboard_addr = 127.0.0.1`, порт 7500 наружу не открывать (на текущем
  сервере дашборд закрыли задачей IPRSV1-16); доступ — через SSH-туннель.

Сгенерированные `token` и `dashboard_pwd` существуют в одном месте — в
`frps.ini` на сервере. Не выводить их в чат, PR, коммиты, `CLAUDE.md` и логи.

Автозапуск — тем же механизмом, что на текущем сервере, службы не заводить и
обёрток (`nssm`, `WinSW`) не ставить:

- Create: `C:\frps\run-frps.bat` — идемпотентный: проверяет `tasklist` на
  живой `frps.exe` и только при его отсутствии делает `cd /d C:\frps` и
  запускает `frps.exe -c frps.ini`;
- задача планировщика `frps` от `SYSTEM`: триггеры «при старте системы» и
  «каждые 5 минут, повторять бесконечно», без `ExecutionTimeLimit`,
  `MultipleInstances IgnoreNew`, перезапуск при сбое 1 минута × 3;
- Create: `C:\frps\frps-watchdog.ps1` + задача планировщика `frps-watchdog`
  каждые 5 минут от `SYSTEM` с `ExecutionTimeLimit PT5M`, со сдвигом
  относительно триггера задачи `frps`: скрипт ничего не делает, пока
  `frps.exe` жив, иначе перезапускает задачу `frps` (сначала
  `Stop-ScheduledTask`, и только если состояние самой задачи `frps` ещё
  `Running`).

Запускать `frps.exe -c frps.ini` руками из SSH-сессии нельзя: поднимется второй
экземпляр, подерётся за 7000 и умрёт вместе с сессией. Запуск и перезапуск —
только через задачу (`schtasks /run /tn frps`).

**7. Файрвол.** Создать входящие разрешающие правила, повторяющие рабочий набор
текущего сервера за вычетом того, что относится к домену и TLS. Имена — в стиле
уже существующих на текущем сервере, с номером задачи:

- `iprsv1-18-cmsv6-tcp` — TCP **80, 2121-2162, 6601-6612, 6617, 6630-6635**
- `iprsv1-18-cmsv6-udp` — UDP **6601-6612**
- `iprsv1-18-frps-tcp` — TCP **7000, 9966, 9967**

Все — `-Profile Any -RemoteAddress Any -Program Any -Action Allow`. Порт 7500
(дашборд frps) не открывать. Порт 443 не открывать: nginx и TLS в эту задачу не
входят. Правила, созданные инсталлятором CMSV6 под своими именами (`GPS *`), не
трогать и не удалять.

Перед созданием и после создания снять число включённых входящих разрешающих
правил, чтобы в документации был точный след изменения.

**8. Проверка снаружи, с раннера.** Ровно те же измерения, что подтверждают
работу текущего сервера:

- TCP на 22 и HTTP-ответ `200` на `http://200.165.238.242/`;
- TCP-подключение на 7000 устанавливается;
- `curl -H "Host: test-unregistered.scanvision.online" http://200.165.238.242:9966/`
  отдаёт `404` от frps — это и есть признак живого vhost: незарегистрированный
  субдомен всегда 404, а сам ответ доказывает, что механизм `subdomain`
  включён;
- TCP на 7500 снаружи НЕ устанавливается.

🔴 Если порт с живым слушателем и разрешающим правилом всё равно не отвечает
снаружи — это фильтрация у хостера нового сервера, а не ошибка настройки
(у хостера текущего сервера фильтрации нет, но это другая площадка). В этом
случае зафиксировать замер и доложить в чат: сами мы такую фильтрацию не снимем.

**9. Документация.** Modify: `CLAUDE.md` в корне репозитория. Файл сейчас
описывает ровно одну машину, и после этой задачи их две — поэтому:

- вводный абзац файла (первые строки до раздела «Connecting to the server»)
  дополнить так, чтобы было явно сказано: репозиторий описывает два сервера
  проекта, и весь существующий текст ниже относится к `201.34.132.26`, если не
  указано иное. Существующие разделы при этом не переписывать и не
  переставлять;
- добавить один новый раздел верхнего уровня «Сервер 2 — 200.165.238.242 (без
  домена)» в конце файла, повторяющий структуру описания первой машины ровно в
  той части, которая на новой машине есть: как подключаться (SSH 22, ключ
  раннеров, пароль), что установлено (версия CMSV6 `7.36.1_20251023` и путь
