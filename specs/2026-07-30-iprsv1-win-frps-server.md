# Что сделать

Вся установка — на сервере по SSH (RDP не нужен), плюс один файл документации в
репозиторий. Ничего не скачивать и не распаковывать.

**1. Конфиг frps.** Modify: `C:\Users\Administrator\Desktop\6e9\frps.ini` на
сервере (это файл на машине, не в репозитории). Перед правкой сохранить копию
исходника рядом как `frps.ini.vendor-backup`, чтобы вендорские значения не
потерялись. Формат оставить INI, раздел `[common]`; итоговый набор ключей:

- `bind_port = 7000` — порт, который слушает сервер для frpc-клиентов: свободен,
  совпадает с вендорским значением и с примером из документации;
- `vhost_http_port = 9966`, `vhost_https_port = 9967` — как в вендорском
  примере, порты свободны;
- `dashboard_addr = 127.0.0.1`, `dashboard_port = 7500`,
  `dashboard_user = admin`, `dashboard_pwd` = сгенерированный на сервере
  случайный пароль (не меньше 20 символов, буквы и цифры). Ключ именно
  `dashboard_pwd`: вендорское `dashboard_passwd` этот бинарь не понимает и
  оставил бы дашборд с дефолтным паролем (см. Контекст). Дашборд наружу не
  публикуется — слушает только localhost, доступ через SSH-туннель;
- `token` = сгенерированный на сервере случайный токен (не меньше 24 символов,
  буквы и цифры) вместо публичного вендорского `coointech81`: frpc-клиентов ещё
  нет, а вендорское значение опубликовано в комплекте поставки и на публичном IP
  означало бы, что тоннель может поднять кто угодно;
- `tcp_mux = true` — как в вендорском примере;
- `log_file = C:\Users\Administrator\Desktop\6e9\frps.log`, `log_level = info`,
  `log_max_days = 7` — процесс будет работать без консоли, лог становится
  единственным источником диагностики;
- строку `subdomain_host` не задавать (удалить или закомментировать) — домена у
  проекта нет. Следствие, которое надо знать и записать в CLAUDE.md: пока ключа
  нет, frps отклоняет http/https-прокси с `subdomain` сообщением
  `subdomain is not supported because this feature is not enabled by frps`; это
  ожидаемое состояние до появления домена.

Сгенерированные `token` и `dashboard_pwd` существуют в одном месте — в
`frps.ini` на сервере. Не выводить их в чат, в PR, в CLAUDE.md, в коммиты и в
логи прогонов: кто будет настраивать frpc, прочитает их по SSH.

**2. Правила файрвола.** Создать входящие разрешающие правила ровно на порты,
которые frps слушает по этому конфигу: TCP 7000 (`bind_port`) и TCP 9966 + 9967
(vhost). Имена — в стиле уже существующих правил машины: `frps-7000-tcp` и
`frps-9966-9967-tcp`, правила по порту (не по программе), как сделаны `CMSv6-*`.
Порт дашборда 7500 в файрвол НЕ открывать. UDP-правил не создавать: `kcp` и
`bind_udp_port` в конфиге не включены.

**3. Первый запуск и проверка.** Запустить сервер из папки, где лежит бинарь:
`frps.exe -c frps.ini`. Успех — в `frps.log` появились строки с текущей датой
`frps tcp listen on 0.0.0.0:7000` и `Start frps success` (вендорская инструкция
ждёт эти строки в консоли; при заданном `log_file` они идут в файл — это то же
доказательство), и порт 7000 виден в `Get-NetTCPConnection -State Listen`. Если
конфиг не распарсился или строк нет — остановиться и разобраться, к автозапуску
не переходить.

**4. Постоянная работа.** Автозапуск оформить задачей планировщика Windows
(модуль `ScheduledTasks` — штатный механизм: обёрток вроде nssm на машине нет и
ставить их нельзя, а `frps.exe` не сервисный бинарь и под `sc create` корректно
не живёт):

- имя задачи `frps`;
- действие: `frps.exe` с аргументом `-c frps.ini` и рабочей папкой
  `C:\Users\Administrator\Desktop\6e9` (без рабочей папки относительные пути
  конфига и лога уедут в `system32`);
- триггер: при старте системы;
- принципал `SYSTEM`, RunLevel Highest — процесс не зависит от входа
  пользователя и не завершается при закрытии SSH-сессии или консоли;
- настройки: без лимита времени выполнения, перезапуск при сбое (интервал
  1 минута, 3 попытки), `MultipleInstances = IgnoreNew`.

Перед регистрацией задачи погасить процесс ручного запуска из п.3, чтобы два
frps не боролись за 7000; после регистрации запустить задачу и снова убедиться
по логу и слушающему порту, что сервер поднялся. Машину НЕ перезагружать — на
ней работает платформа CMSV6; автозапуск подтверждается конфигурацией задачи
(триггер «при старте системы» + принципал SYSTEM) и успешным запуском через
планировщик.

**5. Документация.** Create: `CLAUDE.md` в корне репозитория (файла нет).
Английский, компактно, без значений секретов:

- как подключаться к серверу: SSH на порт **2299**, реквизиты — переменная и
  секреты репозитория `SERVER`, `LOGIN`, `PASSWORD` (в сессии раннера доступны
  как переменные окружения `$SERVER`, `$LOGIN`, `$PASSWORD`); пример команды
  `sshpass -p "$PASSWORD" ssh -p 2299 -o StrictHostKeyChecking=accept-new "$LOGIN@$SERVER"`;
  аутентификация только по паролю, ключей нет;
- шелл по умолчанию `cmd`; многострочный PowerShell подавать на stdin
  (`'powershell -NoProfile -NonInteractive -Command -'` + heredoc) — инлайн-
  кавычки в одну строку ломаются;
- что на машине: платформа CMSV6 (веб на 8080, службы `GPS*`/`gpstomcat6`, MySQL
  на 127.0.0.1:3311) и frps в `C:\Users\Administrator\Desktop\6e9`;
- frps: конфиг `frps.ini` там же, лог `frps.log`, автозапуск — задача
  планировщика `frps` (при старте системы, SYSTEM), `bind_port` 7000, vhost
  9966/9967;
- дашборд слушает 127.0.0.1:7500, наружу закрыт, доступ через туннель
  `ssh -p 2299 -L 7500:127.0.0.1:7500 "$LOGIN@$SERVER"` затем
  `http://127.0.0.1:7500`, пользователь `admin`;
- `token` и пароль дашборда лежат только в `frps.ini` на сервере — в репозиторий
  их не переносить;
- `subdomain_host` сейчас не задан: чтобы включить субдомены, нужен домен с
  wildcard A-записью на адрес из `SERVER`, затем строка `subdomain_host` в
  `frps.ini` и перезапуск задачи `frps`;
- значения `LOGIN`, `PASSWORD`, `SERVER` в файл не писать — только имена и
  порядок использования.
