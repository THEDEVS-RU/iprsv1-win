# Контекст

Новый проект IPRSV1. Единственный его репозиторий — `THEDEVS-RU/iprsv1-win`,
создан 2026-07-30, ветка по умолчанию и единственная — `dev`, в ней лежит один
файл `README.md` (12 байт). Кода, каталога `.github/` и workflow-ов нет:
`repos/THEDEVS-RU/iprsv1-win/actions/workflows` возвращает `total_count: 0`.

Цель задачи — подключиться к серверу проекта (Windows Server 2022) и убедиться,
что машина доступна и работает штатно. Машина внешняя по отношению к нашему
кластеру: в namespace `dev` и `master` подов IPRSV1 нет, поиск по коду
организации THEDEVS-RU по строкам «iprsv1» и «IPRSV» не даёт ничего, кроме
README этого репозитория.

Реквизиты доступа заведены как Actions-секреты и переменные самого репозитория
(именно репозиторные, а не привязанные к окружению: `.../environments` →
`total_count: 0`). Это определяет механизм решения целиком:

- значения Actions-секретов GitHub принципиально не отдаёт через API — их
  нельзя прочитать никаким токеном, они расшифровываются только внутри
  запущенного workflow этого репозитория;
- значит подключение к серверу должно жить в GitHub Actions workflow в
  `iprsv1-win`, а не в скрипте, запускаемом где-то ещё.

Имена ключей в спеке намеренно не названы: токен планирующей стадии получает
403 на `/actions/secrets`, `/actions/variables` и `/actions/runners`, а
выдуманные имена сломали бы workflow. Имена выясняет первый шаг самого
workflow — там они доступны легально и без утечки значений.

# Что сделать

Create: `.github/workflows/health-check.yml` — единственный новый файл задачи.

**1. Триггеры.** Ручной запуск плюс автозапуск при изменении самого файла — так
workflow проверяется прямо на ветке реализации, ещё до слияния (важно: событие
`workflow_dispatch` доступно только для workflow, уже присутствующего в ветке
по умолчанию, то есть до слияния в `dev` кнопки запуска не будет):

```yaml
on:
  workflow_dispatch:
  push:
    paths:
      - '.github/workflows/health-check.yml'
```

**2. Раннер.** `runs-on: windows-latest`. На этом образе уже есть PowerShell 7
(`pwsh`), модули `NetTCPIP`/`Microsoft.PowerShell.Management` и клиент OpenSSH,
поэтому ничего доустанавливать не требуется.

**3. Шаг «Inventory» — выяснить реальные имена ключей.** Печатает только имена;
значения GitHub маскирует сам, поэтому утечки нет:

```yaml
      - name: Inventory
        shell: pwsh
        env:
          SECRETS_JSON: ${{ toJSON(secrets) }}
          VARS_JSON: ${{ toJSON(vars) }}
        run: |
          "secrets: " + ((($env:SECRETS_JSON | ConvertFrom-Json).PSObject.Properties.Name) -join ', ')
          "vars: "    + ((($env:VARS_JSON    | ConvertFrom-Json).PSObject.Properties.Name) -join ', ')
```

Порядок работы: сначала закоммитить workflow с этим шагом, дождаться прогона на
своей ветке, прочитать имена из лога (`gh run view <run-id> --log`) и только
после этого дописать шаги подключения, подставив реальные имена. Ключ
`github_token` в списке секретов присутствует всегда и к серверу отношения не
имеет — его игнорировать.

**4. Шаг «Connect» — подключение по разобранным именам.**

- Хост, порт, логин и пароль (или приватный ключ) прокидываются в шаг только
  через `env:`, в командную строку не подставляются и в лог не печатаются.
- Протокол выбирается по составу найденных имён: ключи вида WinRM → PowerShell
  remoting, ключи вида SSH или приватный ключ → `ssh`. Если по именам это не
  читается, сначала пробуется WinRM, при отказе — SSH; выбранный вариант
  фиксируется в отчёте.
- Перед сессией — проверка TCP: `Test-NetConnection -ComputerName $env:HOST -Port $env:PORT`.
  Закрытый порт означает, что GitHub-раннер не видит машину, и это сам по себе
  результат проверки (см. «Критерии готовности»), а не повод искать обходной
  путь.
- WinRM по HTTP (порт 5985) требует на раннере
  `Set-Item WSMan:\localhost\Client\TrustedHosts -Value $env:HOST -Force`
  (раннер одноразовый, это безопасно). WinRM по HTTPS (порт 5986) — ключ
  `-UseSSL`, а при самоподписанном сертификате ещё и
  `-SessionOption (New-PSSessionOption -SkipCACheck -SkipCNCheck)`.
- Учётные данные собираются внутри шага:
  `New-Object System.Management.Automation.PSCredential($env:USER, (ConvertTo-SecureString $env:PASS -AsPlainText -Force))`.
- Приватный ключ для SSH, если он используется, кладётся во временный файл и
  удаляется в конце шага (`finally`), в артефакты не попадает.

**5. Шаг «Health report» — что собрать в одной удалённой сессии.**

- Имя хоста, название, версия и билд ОС: `Get-ComputerInfo` → `CsName`,
  `OsName`, `OsVersion`, `OsBuildNumber`.
- Аптайм: `(Get-CimInstance Win32_OperatingSystem).LastBootUpTime`.
- Диски: `Get-Volume` — по каждому тому с буквой размер, свободно и процент
  свободного.
- Память: `TotalVisibleMemorySize` и `FreePhysicalMemory` из
  `Get-CimInstance Win32_OperatingSystem`.
- Службы, которые должны работать, но не работают:
  `Get-Service | Where-Object { $_.StartType -eq 'Automatic' -and $_.Status -ne 'Running' }`.
- Ошибки и критические события за сутки:
  `Get-WinEvent -FilterHashtable @{LogName='System','Application'; Level=1,2; StartTime=(Get-Date).AddHours(-24)}`
  — вывести общее количество и 10 последних (время, лог, источник, ID).
- Признак ожидающей перезагрузки: наличие ключа реестра
  `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired`.

**6. Отчёт.** Всё собранное — таблицами в `$env:GITHUB_STEP_SUMMARY`, плюс
первой строкой явный вердикт: `OK` или `ПРОБЛЕМЫ` со списком сработавших
условий.

**7. Красный прогон.** Job завершается ошибкой, если: TCP-порт недоступен, не
прошла аутентификация, на любом томе свободно меньше 10%, есть служба с типом
запуска Automatic не в состоянии Running, либо за сутки найдено хотя бы одно
событие уровня Critical. Всё остальное (события уровня Error, ожидающая
перезагрузка, память) — предупреждение в отчёте, прогон остаётся зелёным.

# Критерии готовности

- В ветке `dev` лежит `.github/workflows/health-check.yml` с ручным триггером и
  автозапуском при изменении самого файла.
- Workflow отработал минимум один прогон, в задачу приложены ссылка на прогон и
  его вердикт.
- В логе прогона видны имена секретов и переменных, и ни одного значения
  секрета в открытом виде.
- Прогон закончился одним из двух однозначных исходов: зелёный с отчётом о
  состоянии машины в summary, либо красный с названной причиной — закрытый
  TCP-порт, отказ аутентификации, порог по диску, неработающая Automatic-служба
  или событие уровня Critical.
- Если машина с GitHub-раннера недоступна, это зафиксировано в задаче как
  результат проверки (нужен self-hosted runner либо доступ снаружи), без
  попыток обойти проверку.

- Значения секретов и переменных: не печатать, не сохранять в файлы (кроме
  временного ssh-ключа, удаляемого в том же шаге), не переносить в README.

  и не создавать новые.

  постоянный мониторинг.
- Новые зависимости (`pywinrm`, Ansible, пакеты choco) не ставить — всё нужное
  есть на `windows-latest`.
- На самой Windows-машине ничего не менять: проверка только читает — не
  перезапускать службы, не устанавливать обновления, не править реестр, не
  перезагружать.
- `README.md` не трогать; CLAUDE.md и прочую документацию в рамках этой задачи
  не заводить.
